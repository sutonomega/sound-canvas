# プロジェクト推進・レビュー対応ガイド

## 基本方針

[mahjong-zukanの開発手順](https://github.com/sutonomega/mahjong-zukan/blob/main/docs/project-workflow.md)をSound Canvas向けに適用する。個人開発でも、Issueの目的・文書・実差分・確認結果を辿れるようにする。

## 計画と文書

- 作業Issueには目的、対応内容、完了条件、関連Issue・文書、確認方法を記載する。
- マイルストーンは成果で区切る。範囲や順序を変更したら、説明とIssue割当、[ロードマップ](roadmap.md)を同時に更新する。
- 実装前に該当する仕様・設計を整える。現状と将来案を混同しない。
- [仕様](spec.md)、[設計](design.md)、[公開範囲](service-scope.md)を実装時の判断基準とする。文書に定めた目標と現在の実装済み機能は区別する。
- 音楽解析、共通描画、個別スタイル、出力の責務を分け、スタイル追加時は共通契約の再利用性も確認する。

## ブランチとPR

1. `dev` から `feat/issue-番号-主題`、`fix/issue-番号-主題`、`docs/issue-番号-主題` 等を作る。
2. 一つのPRを一まとまりのレビュー目的に絞り、`dev` 宛てに提出する。途中の提案はDraftで共有できる。
3. 本文に関連Issue、目的、変更箇所、確認結果と未確認項目、重要な判断を示す。画面変更は画像や操作条件も記録する。
4. レビューと必要な確認後に `dev` に統合する。PR作成、マージ、公開は別の状態として報告する。
5. `main` は既定・公開ブランチとする。`dev` 宛PRの `Closes #番号` は自動クローズを保証しない。完了条件を確認し、マージ先と証拠をIssueに記録して手動で閉じる。公開確認が条件なら公開後まで開いておく。
6. 公開時に `dev` → `main` のPRを作り、確認済み変更をまとめて反映する。例外的な統合先変更はIssueとPRに理由を記録する。

## レビュー指摘と差分

- 別機能への変更、独立して検証・取り消しできる修正、レビュー済み・マージ済みPRへの追加はフォローアップPRに分ける。
- 元PR・指摘・関連Issueを参照する。未マージPRに積む場合は適切なベースを選び、差分重複を避ける。
- 文書はファイル・見出しと修正前後、コードはファイル・行と短いdiffまたはPRの差分リンクを示す。
- 範囲が変わったらPRのタイトル・本文・Issueを最終差分に合わせ直す。

## 確認と完了

- 変更に応じた確認を行う。音楽解析、固定刻み、復元、出力の変更では意味のある自動確認を優先し、見た目・操作・保存はブラウザでも確認する。
- 実施環境、音源の条件、結果、未確認・既知制限を記録し、未実施を成功扱いしない。自作曲などの個人ファイルは許可なくコミットしない。
- マイルストーンは全必須Issueとその成果を確認して閉じる。v1.0の完成条件はロードマップと公開Issue #21に従う。
- GitHub Actionsの成功だけで公開確認を済ませず、公開URLで主要操作を確認する。現在のワークフローはmain公開時にJavaScript構文と自動テストを確認する。PR時CIと広い検証はIssue #21で整備する。
- 完了報告にIssue・PR、変更点、確認結果、未解決事項、公開状態を含める。

## ブランチの棚卸し

PRマージ後に、統合済みかつ固有の未マージ変更がない作業ブランチを確認して削除する。`main`、`dev`、作業中、復旧・退避用ブランチは保持する。削除前にPRと固有コミットを確認し、保持・削除結果を報告する。

## 現在の公開方法

`main` へのpushで `.github/workflows/pages.yml` が `dist/` をGitHub Pagesへ公開する。日常の `dev` 更新だけでは公開されない。

公開先: https://sutonomega.github.io/sound-canvas/
